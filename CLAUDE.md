# MoneyManager

A personal finance tracking app for Android (iOS planned later) built with Flutter. Users log income/expense transactions manually, filter/summarize them by day/week/month/year, and can optionally auto-capture transactions from bank/app notifications using user-configurable regex rules.

## Status

**In active development.** Phases 0–9 are implemented and verified on-device (see [docs/roadmap.md](docs/roadmap.md)).

## Safety rules (for Claude)

- **Never wipe data on the user's physical device without asking first.** The app is local-first with no cloud backup, so uninstalling/reinstalling it (including what `flutter install`/`flutter run` do automatically when a signing mismatch forces an uninstall) permanently destroys the on-device SQLite database. Before any install/uninstall/reinstall targeting a physical device (not the emulator), ask the user first and wait for a yes — never assume it's fine because it worked fine on the emulator. This rule does not apply to the emulator, whose data is disposable.

## Quick facts

- **Platforms:** Android first (testable device available). iOS planned for later — architecture must not block it, but no iOS-specific work happens yet.
- **Framework:** Flutter (Dart) — single codebase shares UI + logic across Android/iOS later. See [docs/architecture.md](docs/architecture.md).
- **Local storage:** On-device SQLite via Drift. Fully local-first; no account required to use the app.
- **Backup:** Local file import/export (no account/cloud) — see [docs/features/data-import-export.md](docs/features/data-import-export.md).
- **Notification capture:** Android `NotificationListenerService` (native Kotlin) bridged to Flutter via a platform channel/plugin. Regex-based rule matching extracts amount + income/expense type from bank/app notifications. See [docs/features/notification-capture.md](docs/features/notification-capture.md).

## Key decisions log

- **Flutter over Kotlin Multiplatform/React Native/native-only**: user wants eventual iOS support from one codebase; Flutter has the most mature single-codebase story. Native Android code is still required for the notification listener (Flutter can't access `NotificationListenerService` directly).
- **Local-first with optional cloud backup**: avoids building/maintaining a backend for v1; local-first keeps data private and offline-capable. Cloud backup (Google account-based) is a planned addition, not MVP.
- **Notification rules are configurable per-rule for auto-add vs. review-queue**: balances convenience (trusted rules auto-add) against safety (new/uncertain rules land in a review queue before counting toward totals).
- **Scope for v1 transaction model**: categories, multiple accounts/wallets (with transfers), notes + source-app tagging, and recurring transactions are all in scope (not deferred) per user request — see [docs/data-model.md](docs/data-model.md).
- **Local file import/export over cloud backup** (2026-11-06): replaced the earlier Google Drive/Firebase backup plan — no account, sign-in, or network call for backup/restore, ever. The user picks the file's location themselves via Android's own file picker. See [docs/features/data-import-export.md](docs/features/data-import-export.md).
- **No periodic/background work for notification-capture reliability** (2026-11-06, Phase 9, explicit user requirement): `requestRebind()` runs only on `MainActivity` launch and on manual "Recheck" tap, never on a timer/`WorkManager`; battery-optimization status and listener diagnostics are read on-demand (screen view / app resume) only, never polled; no foreground service was added. Also chose `Settings.ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS` (generic settings list) over `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` (direct exemption dialog) to avoid Play Store policy risk. See [docs/features/background-reliability.md](docs/features/background-reliability.md).
- **Transaction date field now includes time** (2026-11-08, user request): the add/edit transaction sheet's date field changed from date-only (`yyyy-MM-dd`) to date+time (`dd/MM/yyyy HH:mm:ss`); transaction list rows now show the time too. The underlying `Transaction.date` column was already a full datetime — only the entry/display UI was date-only. See [docs/features/transactions.md](docs/features/transactions.md).
- **Removed notification duplicate-protection check** (2026-11-08, user request): `NotificationCaptureService.handle()` no longer skips inserting a transaction when an identical-looking one (same rule/app/amount/resolved date) already exists. The user asked for this as a suspected cause of transactions going missing while the app was closed; Phase 9's investigation didn't actually confirm that mechanism, but the check was a convenience against Android's occasional notification redelivery, not a correctness requirement, so it was removed on request rather than contested. Trade-off: a redelivered notification can now produce a duplicate transaction the user has to delete manually. See [docs/features/notification-capture.md](docs/features/notification-capture.md) "Matching details".
- **Backup screen consolidation** (2026-11-08, user request): the Settings drawer's four backup rows ("Export data"/"Import data"/"Export rules"/"Import rules") were replaced with a single "Backup" row navigating to a new `BackupScreen`, which groups them into two labeled lists — "All data" (full DB export, which already includes notification rules) and "Notification rules only". Shared row/spinner widgets (`SettingsRow`, `BusyIndicator`) were extracted out of `settings_drawer.dart` into `lib/features/settings/presentation/widgets/settings_row.dart` so both the drawer and the new screen use them. See [docs/features/settings-drawer.md](docs/features/settings-drawer.md) and [docs/features/rules-import-export.md](docs/features/rules-import-export.md).
- **Dashboard: transactions moved above reports** (2026-11-08, user request): the transaction list now sits directly below the all-time balance card, ahead of Cash flow/By category/By account, instead of at the bottom of the dashboard. See [docs/features/transactions.md](docs/features/transactions.md) "List view".
- **All-time balance: excludes archived accounts + manual adjustment added** (2026-11-08, user request): the user found that archiving an account didn't remove its balance from the dashboard's all-time balance. Root cause: `TransactionsRepository.watchAllTimeBalanceMinorUnits()` summed every account/transaction with no `is_archived` filter, unlike `AccountsRepository.watchActive()`/`watchActiveWithBalances()` which already excluded archived accounts elsewhere in the app — fixed to match. Additionally, per the user's explicit ask to "modify all-time balance", added `AppSettings.all_time_balance_adjustment_minor_units` (a stored delta, not a frozen override) plus a "set what this should show" sheet on the balance card (tap its edit icon), so new transactions keep affecting the total after the correction. See [docs/data-model.md](docs/data-model.md) "Derived/computed" and [docs/features/categories-accounts.md](docs/features/categories-accounts.md).
- **Cash Flow custom date range + settings entry point widened** (2026-11-08, user request): the Cash Flow period selector gained a "Custom" option (`Period.custom`, `DateRange.customRange()`) opening Flutter's built-in `showDateRangePicker` for an arbitrary start/end range, with prev/next shifting by the range's own span rather than a calendar unit. Separately, for settings discoverability the user was given the choice of moving the gear icon top-left or widening the drawer's swipe-to-open zone — both were done rather than picking one (`drawerEdgeDragWidth: 48`). See [docs/features/transactions.md](docs/features/transactions.md) and [docs/features/settings-drawer.md](docs/features/settings-drawer.md).
- **Archived accounts made visible + unarchivable; all-time-balance inclusion made a toggle** (2026-11-09, user request): the Accounts screen now has an "Archived accounts" section below the active list (`AccountsRepository.watchArchivedWithBalances()`), and the add/edit account sheet's "Archive" button becomes "Unarchive" for an already-archived account (`AccountsRepository.unarchiveAccount()`, no confirmation dialog — unlike archiving). The 2026-11-08 fix that hard-excluded archived accounts from the all-time balance was made configurable instead: new `AppSettings.include_archived_in_all_time_balance` (default `false`, preserving that fix's behavior), toggled via a switch on the new Archived accounts section, read by `TransactionsRepository.watchAllTimeBalanceMinorUnits()`. See [docs/features/categories-accounts.md](docs/features/categories-accounts.md) and [docs/data-model.md](docs/data-model.md) "Derived/computed".
- **Permanent account delete, gated on being unused** (2026-11-09, user request, follow-up to the above): accounts previously could only ever be archived, never removed outright. Added `AccountsRepository.isUnused()` (true only when no `Transaction`, `RecurringTransaction`, or `NotificationRule.defaultAccountId` references the account) and `deleteAccount()`; the edit sheet shows a "Delete permanently" action, confirmed via dialog, only when `isUnused()` is true — an account with any history stays archive-only, so this can't lose transaction data or break a foreign key. See [docs/features/categories-accounts.md](docs/features/categories-accounts.md).
- **"Insert from text" manual notification entry** (2026-11-13, user request, "insert a text message and will check all rules and if one matches it, insert as a transaction... this way i can insert missed notifications"): new Settings row opening `ManualTextEntryScreen`. Pasted text is matched against every *enabled* rule regardless of app package (new `NotificationRulesRepository.enabledRules()`, since there's no real notification package to filter by) via a refactored `NotificationCaptureService` (`handle()`'s insert tail extracted into a shared `_insert()`, plus new `matchManualText()`/`insertManualMatch()`). Unlike live/headless capture, this is a two-step preview-then-confirm flow — matching alone writes nothing; the user reviews the resolved rule/amount/account/category/note/date (date falls back to "now" if the rule has no date group) before explicitly tapping "Insert transaction". See [docs/features/notification-capture.md](docs/features/notification-capture.md) "Manual text entry".
- **Bottom navigation bar: Transactions/Reports/Accounts tabs, replacing the single-screen Dashboard** (2026-11-13, user request): added `MainScreen` (`lib/app/main_screen.dart`) as the app's new root — a `Scaffold` with a 3-item `NavigationBar` over an `IndexedStack` of `TransactionsTab`, `ReportsTab` (new, under `lib/features/reports/presentation/`), and the existing `AccountsScreen` (moved from a Settings-drawer row to a primary tab; removed from `SettingsDrawer`). `TransactionsTab` carries over the old Dashboard's greeting/currency header, balance card, and period filter, but replaces the just-added 10-at-a-time "Load more"/"Show all" pagination with true infinite scroll (`CustomScrollView` + a `ScrollController` threshold that grows a client-side visible-count — no DB-level pagination needed, since `watchPeriodTransactions()` already returns the whole period reactively). `ReportsTab` got the Cash flow/By category/By account sections that used to sit below the transaction list, with its own copy of the period filter (same shared `activeDateRangeProvider`, so it stays in sync with the Transactions tab). The Settings drawer (gear icon/edge-swipe) now attaches to `MainScreen`'s root `Scaffold` instead of the old Dashboard's, so it's reachable the same way from every tab; the "Add transaction" FAB similarly moved to `MainScreen` and hides on the Accounts tab. See [docs/architecture.md](docs/architecture.md) "Navigation", [docs/features/transactions.md](docs/features/transactions.md) "List view", [docs/features/reports.md](docs/features/reports.md) "Placement".
- **Dashboard transaction list: filter moved above the list, paginated 10-at-a-time, "Show all" full screen; date entry switched to pickers** (2026-11-13, user request, superseded by the bottom-nav change above — kept here for history): the period filter (`PeriodSegmentedControl`/`PeriodNavigator`) moved from above "Cash flow" to directly above the transaction list on the dashboard (still the same shared `activeDateRangeProvider`, so Cash flow/By category/By account are unaffected) so changing it doesn't need scrolling past the list first. The dashboard list itself now shows only 10 transactions with a "Load more" button (+10 each tap, resets to 10 on period change — see `TransactionListSection` in `lib/features/transactions/presentation/widgets/transaction_list_section.dart`); a new "Show all" link opens `AllTransactionsScreen`, a full screen with the same filter and the complete unpaginated list. Separately, the add/edit transaction sheet's and the transfer sheet's free-text date fields were replaced with tap-to-pick (`showDatePicker` + `showTimePicker` for transactions, `showDatePicker` only for transfers, which are date-only) — see [docs/features/transactions.md](docs/features/transactions.md) "List view" and "Add / edit / delete".
- **Samsung-specific background guidance + boot/update rebind + headless-outcome diagnostics** (2026-11-12, user report: S23 Ultra, capture stops ~30 min after app close): diagnosed as One UI's own "Background usage limits" classifier (distinct from, and independent of, the standard Android battery-optimization exemption already prompted for). Added a Samsung-only guidance banner (`getDeviceManufacturer`/`openOemBackgroundSettings` in `MainActivity.kt`, `_SamsungBackgroundBanner` in `rules_screen.dart`), an event-driven (not periodic) `BootAndUpdateReceiver` for `BOOT_COMPLETED`/`MY_PACKAGE_REPLACED`, and persisted last-headless-dispatch-outcome diagnostics (`NotificationBridge.saveHeadlessDispatchOutcome`) surfaced on the existing diagnostics card. Did **not** add a foreground service or any polling — that remains ruled out per the 2026-11-06 decision; flagged as an explicit, user-approval-only option if the above proves insufficient on this device. Selected via an abbreviated arena-skill tournament (stopped after a partial Round 1 to save budget, per user request) rather than a full 7-round run. On-device verification (2026-11-13) on the real S23 Ultra found the Samsung deep link's hardcoded activity class name doesn't exist on this device's One UI version; fixed by switching to the action-based intent `com.samsung.android.sm.ACTION_BATTERY`, confirmed working after the fix. See [docs/features/background-reliability.md](docs/features/background-reliability.md) "Samsung One UI follow-up".
- **Foreground service added to the notification listener** (2026-11-14, user request, reverses part of the 2026-11-06/11-12 no-foreground-service decisions): user reported notifications were still missed after the phone sat idle overnight (app closed), confirming the earlier mitigations weren't sufficient — exactly the condition those decisions said to revisit under, with explicit user opt-in now given for the trade-off (a permanent low-priority notification icon while capture is active). `NotificationCaptureListenerService` now calls `startForeground()`/`stopForeground()` in `onListenerConnected()`/`onListenerDisconnected()`, promoting its own process to foreground priority (same mechanism a music player uses) instead of adding a separate always-on service. Manifest gained `FOREGROUND_SERVICE`/`FOREGROUND_SERVICE_SPECIAL_USE`/`POST_NOTIFICATIONS` permissions and `foregroundServiceType="specialUse"` (no better-fitting standard type exists) with its required `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` justification; `MainActivity` requests `POST_NOTIFICATIONS` once per launch (Android 13+). Still no periodic/polling work anywhere. See [docs/features/background-reliability.md](docs/features/background-reliability.md) "Foreground service promotion".
- **Fixed stale live-dispatch sink causing silently dropped notifications** (2026-11-14, same-day follow-up to the above): user then found capture failing even right after a fresh launch/foreground — a separate bug from idle-reliability, exposed by the foreground-service change just above. Root cause: `NotificationBridge.activeEventSink` could point at a dead engine's sink after Activity/engine teardown (Flutter doesn't reliably call `EventChannel.onCancel` on engine destroy), which the listener happily called `.success()` on, silently losing the notification instead of erroring. Previously masked because the whole process usually died with the engine; the new foreground service keeps the process alive past engine teardown, widening this window. Fixed with `MainActivity.cleanUpFlutterEngine()` clearing the sink on teardown, plus a try/catch fallback to headless dispatch in `NotificationCaptureListenerService.onNotificationPosted()` if a live dispatch ever still fails. See [docs/features/background-reliability.md](docs/features/background-reliability.md) "Stale live-dispatch sink fix".
- **Fixed backup import failing on older exports + disabled Android's silent Auto Backup** (2026-11-18, found while debugging a user report that their old backup wouldn't import): `BackupRepository.parseImport()` only defaulted missing keys for `appSettings` fields, not for `Account.isDefault` (added earlier the same day, non-nullable), so any backup from before that column existed failed with "missing expected data." Fixed with the same per-row defaulting pattern; see [docs/features/data-import-export.md](docs/features/data-import-export.md). Separately discovered `AndroidManifest.xml` never disabled Android's OS-level Auto Backup (`allowBackup` defaults to `true`), so the phone's data was silently round-tripping through the user's Google Account cloud backup on every reinstall — contradicting the "no cloud, ever" decision above. Set `android:allowBackup="false"` to close that gap.
- **Duplicate notifications re-added as a review-queue flag (not a silent skip); category/account filters; default account** (2026-11-18, user request): three changes landed together. (1) Duplicate detection is back (replacing the 2026-11-08 removal), but as a non-destructive flag rather than the old skip-insert behavior: a notification/headless match identical to an existing one (same rule/app/amount/resolved date) still inserts, but gets `Transaction.duplicate_of_transaction_id` set and is forced into the review queue regardless of the rule's `auto_add`, with a "possible duplicate" banner — see [docs/features/notification-capture.md](docs/features/notification-capture.md) "Matching details". (2) Multi-select category/account filters (`TransactionFilterButton`, `lib/features/transactions/presentation/filter_providers.dart`) on both the Transactions and Reports tabs, alongside the period filter — see [docs/features/transactions.md](docs/features/transactions.md) "Filtering by category / account". (3) `Account.is_default` + `AccountsRepository.setDefault()` pre-fills the account field on new manual transactions and new notification rules; this also surfaced and fixed a real pre-existing gap — the add/edit transaction sheet had no account picker at all before this, every manual transaction silently went to the first active account — see [docs/features/categories-accounts.md](docs/features/categories-accounts.md) "Default account". Schema bumped to v5 (`is_default`, `duplicate_of_transaction_id`).
- **Category delete/color/icon (Phase 1 of a 6-phase feature set)** (2026-11-20, user request): categories can now be permanently deleted when unused (mirrors the 2026-11-09 account delete — `CategoriesRepository.isUnused()`/`deleteCategory()`), and can have a user-chosen icon/color, wiring up the `Category.icon`/`color` columns that existed since the original schema but were previously unused in favor of a fixed name-based lookup. `categoryStyle()` now takes the `Category` row itself and prefers its stored icon/color, falling back to the old name-based lookup for anything not yet customized. See [docs/features/categories-accounts.md](docs/features/categories-accounts.md). This is the first of 6 planned phases (remaining: expense/income-separated category filters, per-account all-time-balance inclusion + balance masking, a transaction description field, a notification-rule custom fallback name, and — if feasible — an installed-app picker for the rule editor's package field).
- **Transaction description field (Phase 4 of 6)** (2026-11-20, user request, explicitly confirmed via `AskUserQuestion` as a new, separate field rather than a rename of the existing "Name"/`note` field): new nullable `Transaction.description` column (schema v5→v6, migration `addColumn`), a "Description (optional)" field in the add/edit transaction sheet (shown directly under "Name"), and display as a muted second line under the category/date line in both the transaction list and the review queue. Being nullable, no backup-import compatibility fix was needed (unlike the non-nullable `Account.isDefault` fix from 2026-11-18) — confirmed via a new regression test that an older export missing the `description` key still imports cleanly. Verified on-device: the schema migration preserves pre-existing transactions, and a description typed into an existing transaction persists and displays correctly after save. See [docs/features/transactions.md](docs/features/transactions.md) "Add / edit / delete" and "List view".
- **Notification-rule custom fallback name (Phase 5 of 6)** (2026-11-20, user request): new nullable `NotificationRule.fallback_name` column (schema v6→v7), overriding the rule's own `name` as the `Transaction.note` fallback (used when `name_group` is unset or doesn't match) without changing the rule's display name in the Rules screen — e.g. a rule named "Bank X — card payment v2, excludes refunds" can still produce a short note like "Card payment". A "Fallback name (optional)" field was added to the rule editor sheet, right under "Rule name"; `rule_matcher.dart`'s `_resolveNote`/`testRule` both prefer it over the rule name when set (non-blank). Both the full backup (`BackupRepository`) and the rules-only export (`RulesBackupRepository`, which manually lists `NotificationRule` fields rather than round-tripping generically) were updated to carry the new field through; being nullable, no compatibility fix was needed for older exports — confirmed via new regression tests in both. See [docs/features/notification-capture.md](docs/features/notification-capture.md) "Matching details" and [docs/data-model.md](docs/data-model.md) `NotificationRule`.
